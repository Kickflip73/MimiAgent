# MimiAgent 个人贾维斯产品蓝图

日期：2026-09-04

状态：当前产品与研发基线 v3.0

本文取代旧的 [个人贾维斯建设蓝图](20260727-MimiAgent-个人贾维斯建设蓝图.md)。
旧文档继续作为历史设计和验收记录保留，但不再指导下一阶段开发。

## 1. 先说结论

MimiAgent 的方向没有变：它要做的是一个长期在线、了解 owner、能调用电脑和各种服务、
能把事情持续办完的个人贾维斯。

但实现方向需要收窄：

> Mimi 不亲自成为最强的编程 Agent、研究 Agent 或浏览器 Agent。Mimi 负责理解你、
> 记住你、选择最合适的能力、持续跟进任务、验收结果，并在合适的时候主动出现。

理想的使用过程只有这一条：

你说一句话 → Mimi 理解真正目标 → 简单事情直接做 → 专业事情交给专业 Agent →
后台持续跟进 → 检查结果 → 向你汇报 → 记住对以后有用的信息。

所以 Mimi 的竞争对象并不只是 Codex 或 Claude Code。它要成为这些专业 Agent 的上层个人
总管。Codex 可以比 Mimi 更会写代码，但 Codex 不必长期知道你的生活、工作、偏好和所有
未完成事项；这正是 Mimi 应该承担的位置。

## 2. 关于你担心的权限问题

上一版把太多篇幅放在权限、Outcome、回执和 uncertain 上，读起来像在建设一个安全平台。
这是路线表达错了。

Mimi 的产品级权限规则只保留一句话：

> Mimi 默认在当前操作系统用户已经拥有的权限内工作；owner 明确让它做的事情就直接做；
> Plan 模式只分析和规划，不执行。

不再建设 Safe、Workstation、Full Owner 等多档模式，不建设复杂审批流，不建设人物、
来源、模式和工具之间的权限矩阵，也不让用户频繁点确认。

上一版提到的两句话，翻译成人话是：

- “owner 明确要求的发送、删除、配置、部署直接执行”，本意就是不拦你，不是增加限制。
- “uncertain 不自动重放”，本意是发送请求超时后先检查是否已经发出，不要不分青红皂白再
  发一次。它是避免重复发送的程序正确性，不是权限审批。

这些底层细节不再作为产品能力宣传，也不应占据路线中心。系统只保留三条最低限度：

1. 网页、邮件或聊天消息里的文字不能冒充 owner 给 Mimi 下命令。
2. 一个外部动作结果不明确时，先查结果，再决定是否补做，避免重复发送、支付或删除。
3. Mimi 使用现有系统和账号权限，不另外造一套权限管理平台。

## 3. Mimi 现在到底处于什么阶段

Mimi 现在处于第一阶段：**先变得真正好用**。

仓库里其实已经有很多后续能力：常驻 Daemon、Session、MemoryHub、Goal、Plan、后台 Task、
Schedule、Skills、MCP、Connector、SubAgent、Computer 和多 Provider。这说明地基并不差，
也不需要推倒重来。

真正的问题是“零件很多，但主链路还没有足够顺”：

1. 有些 Provider 的工具结果衔接不一致，可能造成重复调用或卡住。
2. 有些工具实际失败后，运行记录仍可能把它当成成功。
3. 清空对话后，旧 Context 仍有机会重新进入后续请求。
4. 简单问题也可能经过过长的 Context、Memory、工具策略和模式装配，导致慢和不稳定。
5. 可选能力未就绪时，会影响整体健康感受。
6. 主动提醒、人物关系、团队角色等外围设计走得比核心使用体验更快。

因此现在的瓶颈不是“权限不够”，也不是“还缺一个更大的架构”。瓶颈是：

> Mimi 还没有把最常用的十几类任务做成稳定、快速、可离开的完整闭环。

架构方向本身没有根本错误，但开发顺序曾经偏向“把未来能力都搭出来”，导致广度超过了
闭环深度。接下来要暂停横向扩张，先打通最短主链路。

## 4. 最终架构，用人话解释

最终只需要五部分。

### 4.1 常驻管家

负责让 Mimi 一直在线，接收对话、定时任务和外部事件；任务可以在后台继续，重启后也能
恢复。对应现有 Daemon、Event、Task、Schedule 和 Outbox。

### 4.2 Mimi 大脑

负责理解你的话、结合当前对话和长期记忆、判断下一步、决定自己做还是委派。这里主要依靠
模型，不把人物关系、项目管理、承诺管理分别做成程序。

### 4.3 执行能力

文件、Shell、网络等高频能力直接提供；浏览器、电脑操作、日历、消息、邮件通过 Skill、
MCP 或 Connector 接入；编程、研究等复杂任务交给专业 Agent。

### 4.4 持续任务

所有自然语言请求都先交给主模型理解和决策。模型判断可以在当前运行中完成的事情，就直接
使用必要工具完成；需要几个小时、跨多步或跨重启的事情，才创建简单的 Goal、Plan 和
Checkpoint。它们只是为了接着干，不发展成工作流平台。

这里不存在关键词匹配、快捷指令、规则路由或绕过模型的“简单任务处理器”。所谓轻量路径，
只是同一个模型运行时少加载无关 Memory、Goal、Team、Connector 和工具说明，让模型更快、
更专注地完成当前请求。

### 4.5 记忆与结果

Session 保存完整对话，MemoryHub 保存对未来有用的自然语言记忆，执行记录保存“做了什么、
是否完成、结果在哪里”。三者不互相冒充，也不建立人物、项目、承诺等平行业务数据库。

整个系统的主链路应当收敛为：

入口 → 理解上下文 → 选择能力 → 执行或委派 → 检查结果 → 回复与记忆

CLI、Daemon、SubAgent 和未来语音入口都复用这条链路，不再各自拼一套运行逻辑。

## 5. 五个阶段，以及做完后你会感觉到什么

阶段周期是单人项目的粗略节奏，应该根据验收结果调整，而不是为了赶日期跳阶段。

| 阶段 | 核心目标 | 做完后的真实使用变化 |
|---|---|---|
| 1. 先变得好用 | 修主链路、减少卡顿和假成功 | 简单任务响应快；工具失败会明确说失败；清空真的清空；不会无故重复动作 |
| 2. 能把一件事办完 | 后台执行、专业 Agent 委派、结果验收 | 你说“把这个 Bug 修好”，可以离开，回来直接看结果，不必一步步盯着 |
| 3. 能记住并接着干 | 记忆、Goal、Plan、Checkpoint 真正串起来 | 隔天继续时不用重新解释背景；长期任务知道做到哪里、下一步是什么 |
| 4. 开始主动接管 | 接入少量真实来源，主动筛选和执行 | Mimi 会主动告诉你真正重要的事，能按你设定的规则跟进，同时没有变化时保持安静 |
| 5. 扩展到生活和设备 | 浏览器、电脑、语音、移动端和设备能力包 | 你可以在不同入口叫它办事，它能跨软件完成生活与工作事务 |

### 阶段 1：先变得好用

建议周期：2 到 4 周。

只做五件事：

1. 修复 Provider 工具结果、工具失败误记成功、清空 Context 和 Daemon 实例归属问题。
2. 所有请求继续走大模型；普通问答、单文件操作和一次工具调用只装载最小相关上下文与工具。
3. 默认只加载当前真正可用、与请求相关的能力。
4. 把自动 Routine 改成用户主动开启，关闭默认噪声。
5. 建立一组固定真实任务，每次改动都实际跑一遍。

完成后的直观体验：

- “读这个文件并总结”不再先装载一堆无关系统。
- “执行这个命令并告诉我结果”不会把报错说成成功。
- 输入 clear 后，旧话题不会莫名其妙回来。
- 某个可选 Connector 没配置，不会让整个 Mimi 看起来坏了。
- 同一件事不再因为 Provider 差异重复调用工具。

阶段退出条件不是模块完成，而是约 20 个日常任务连续多轮都能稳定完成，且速度和结果可以
接受。

### 阶段 2：能把一件事办完

建议周期：4 到 6 周。

这一阶段先只打通一个最有价值的专业 Agent：Codex。

Mimi 负责接收目标、补足个人和项目上下文、启动 Codex、等待进度、处理需要你决定的问题、
验收测试和最终汇报。Codex 负责代码搜索、修改和测试。二者不重复实现彼此的能力。

完成后的直观体验：

- 你只需要说“修复这个仓库的登录 Bug，跑完测试后告诉我”。
- Mimi 在后台管理这项工作，你可以继续聊别的或关闭窗口。
- Codex 卡住时 Mimi 知道卡在哪里，需要你决定时只问关键问题。
- 最终回复包含实际改动、验证结果和剩余风险，而不是一句“应该完成了”。
- 同样的委派接口以后可以接研究 Agent、浏览器 Agent，而不重做任务系统。

### 阶段 3：能记住并接着干

建议周期：4 到 8 周。

保留现有 MemoryHub，但做减法和性能优化：

- 人物、项目、偏好和承诺用带来源、时间的自然语言记忆表达。
- 只召回当前任务真正相关的内容，不在每次请求扫描和注入全部记忆。
- 长任务只保存目标、当前步骤、关键结果和恢复点。
- 记忆整理放后台，失败不阻断当前对话。
- owner 的纠正可以覆盖旧判断，并保留来源。

完成后的直观体验：

- 你说“继续上次 Mimi 的性能问题”，它知道指什么。
- 你不必每次重述常用仓库、表达偏好和工作习惯。
- 任务中断或机器重启后，可以从最近一个可靠步骤继续。
- 它能解释为什么记得某件事，也可以按你的要求忘掉。

### 阶段 4：开始主动接管

建议周期：6 到 10 周。

不要一开始监听所有东西。先选择两个 owner 每天真实使用的来源，例如日历加一个消息渠道，
或者代码仓库加任务系统。

把现有 Routine、Watch、Briefing 等概念合并到 Schedule；主动决策只保留四种结果：

- 忽略；
- 记入摘要；
- 提醒 owner；
- 执行 owner 已明确开启的自动任务。

完成后的直观体验：

- 重要会议临近、关键任务失败或等待你决定时，Mimi 主动出现。
- 普通消息和没有变化的监测不打扰你。
- 每个主动行为都能回答“因为哪条信息、哪项长期任务或哪条你设置的规则”。
- 你可以用一句自然语言开启、暂停或调整自动任务。

### 阶段 5：扩展到生活和设备

这是持续演进阶段，不设“一次做完”的大版本。

浏览器、Computer Use、语音、移动端、家庭设备、图像和更多消息渠道都作为独立能力包接入。
每个能力包可以单独启用、单独测试、单独失败，不阻塞 Mimi 核心。

完成一个能力包后的变化应该是一个真实场景被打通，例如：

- “帮我在网页上完成报销并把凭证存到指定目录。”
- “我在手机上说一句，电脑上的后台任务继续执行。”
- “出门前告诉我下一场会议、路程和必须带的东西。”

没有明确真实场景的能力包不开发。

## 6. 现有能力怎么处理

### 6.1 保留，继续作为地基

- Daemon、Event、Task、Run、Schedule、Outbox 的可靠执行框架；
- Session 与完整 transcript；
- MemoryHub 的自然语言记忆和检索能力；
- Goal、Plan、Checkpoint 的长任务恢复能力；
- Skills、MCP、Connector 的扩展方式；
- 文件、Shell、Web 等高频基础工具；
- Provider Gateway、Trace、执行结果和回执；
- 一个 Session 同一时间只有一个主执行者的约束。

这些能力有价值，问题主要在组合方式和主链路，不应推倒重建。

### 6.2 优化和精简

- 把 Conversation、Daemon、SubAgent 的运行装配合并为一条共享执行链路。
- 将中央超大 Tool Policy 缩成能力目录，只描述名称、是否可用、是否只读和如何调用。
- 普通请求使用最小 Context；重 Context、Memory 整理和压缩转到后台。
- Provider 差异放进 Adapter，不让主运行时到处判断。
- Attention 只负责是否打扰 owner，不再承担人物系统和复杂来源策略。
- Routine、Watch、Briefing 合并进 Schedule。
- SubAgent 和 Team 收敛成“专业执行器”，先支持一个层级，不建设组织架构。
- Browser、Computer、消息、语音等可选能力独立报告状态，不进入核心全局门禁。

### 6.3 停止扩建，并在迁移完成后删除

- People 语义系统和人物 CRUD；
- 项目、承诺、Case、Follow-up 等专用数据库；
- 通用 Workflow 和复杂状态机；
- Safe、Workstation、Full Owner 多档权限产品；
- People × Source × Mode × Tool 权限矩阵和复杂 Source Policy；
- 固定的 planner、builder、verifier 等 Team 角色体系；
- Routine、Watch、Briefing 各自维护一套重复状态；
- 默认自动创建的主动 Routine；
- “所有可选能力都通过，核心才算可用”的总门禁；
- 为低频场景继续增加内置 Tool。

这里的“删除”不是立即删文件。先让新主链路接管真实流量，确认没有调用者后再删除旧实现和
迁移兼容代码。

## 7. 专业 Agent 应该怎么接

Mimi 与专业 Agent 的分工保持简单：

| 角色 | 负责什么 |
|---|---|
| Mimi | 理解 owner、保存上下文、拆解目标、选择执行器、跟进、验收和最终回复 |
| Codex | 搜索代码、修改代码、运行测试、提供代码证据 |
| 研究 Agent | 搜集资料、比较来源、形成研究结论 |
| 浏览器或电脑 Agent | 操作网页和本机界面，返回动作结果 |
| Connector | 连接日历、消息、邮件、任务系统等外部服务 |

专业 Agent 不拥有 Mimi 的长期人格和全部私人记忆，只接收完成当前任务所需的最小上下文。
Mimi 不把专业 Agent 的过程文本全部塞回长期记忆，只保留目标、关键决定、结果和后续事项。

## 8. Mimi 最终可以在哪些方面形成自己的优势

Mimi 不需要在单次代码生成上超过 Codex，也不需要在单次深度研究上超过专用研究 Agent。
如果以这些单项能力为竞争目标，小团队很难赢。

Mimi 可以形成四个组合优势：

1. **真正了解一个 owner**：上下文跨天、跨项目、跨渠道连续，而不是每个工具重新认识你。
2. **负责把事情办完**：不止给建议，还负责委派、等待、恢复、验收和跟进。
3. **使用最强的现成能力**：底层模型和专业 Agent 可以替换，Mimi 保留个人上下文和任务连续性。
4. **本地、开放、可改造**：数据和运行权主要在 owner 手里，能力通过 Skill、MCP 和 Connector
   按需要增加。

它不一定在“谁最会写代码”这条轴上超过强 Agent，但有机会在“谁最像我的长期个人总管、
谁能跨领域把我的事情持续办完”这条轴上形成更好的个人体验。

## 9. 接下来最实际的开发顺序

不要同时开多个大工程，严格按以下顺序：

1. **修真问题**：先解决审计里的工具结果、假成功、Context clear、Daemon 归属和默认主动行为。
2. **精简模型运行链路**：请求仍由大模型理解和执行，但普通问答、文件、Shell 和 Web 请求
   不装载无关的长期任务、团队编排和全部能力目录。
3. **打通 Codex 委派闭环**：从一句 owner 请求开始，到后台执行、测试验收、最终回报结束。
4. **再做连续性**：让同一个任务跨会话和重启可以继续，并只召回真正相关的 Memory。
5. **最后做主动性试点**：只接两个真实来源和一个高价值自动任务，观察一个月再扩展。

如果第 3 步还不能稳定做到“交给它后可以离开”，就不进入大规模多模态、更多 Provider、
更多 Connector 或复杂主动智能开发。

## 10. 防止项目再次变臃肿的规则

新增能力时依次问：

1. 模型结合现有上下文能不能直接完成？
2. 能不能写成一个 Skill？
3. 能不能通过 MCP、Connector 或专业 Agent 接入？
4. 现有 Session、Memory、Goal、Task 或 Schedule 能不能表达？
5. 只有反复出现、必须确定性执行、并且现有机制无法承载时，才增加内核概念。

同时遵守：

- 一个事实只能有一个权威状态源。
- 新抽象必须解决已经出现多次的真实问题。
- 新模块最好替代旧模块，而不是长期并存。
- 每个阶段都用真实任务验收，不以代码量、工具数和模块数作为进度。
- 没有改善 owner 使用体验的架构工作不排在主路线前面。

## 11. 当前路线定位

截至 2026-09-04：

- 产品方向：个人贾维斯，不是通用工作流平台，也不是第二个 Codex。
- 当前阶段：阶段 1，先变得好用。
- 当前首要指标：常用任务成功率、响应速度、结果真实性、可离开程度。
- 当前冻结项：新领域系统、新 Team 角色、新 Provider、新媒体能力和大规模 Connector 扩张。
- 下一个里程碑：稳定完成一组真实日常任务，然后打通第一个 Codex 委派闭环。
